# みんなの体感リポート（エリア別 台風体感投稿）設計書

- 作成日: 2026-08-15
- 対象: typhoon-risk-navi (iOS / SwiftUI)
- ステータス: 設計承認済み・実装計画待ち

## 1. 目的

台風接近中、公式の警報や進路図だけでは分からない「いま現地がどうなっているか」をユーザー同士で共有する。
沖縄を10エリアに分け、各エリアの体感を色・表情・平易な言葉で投稿し、集約結果を一覧できるようにする。

公式情報の代替ではなく、体感の補助情報として提供する。画面には常に「みんなの体感（公式情報ではありません）」を表示する。

## 2. 前提（調査で確認済み）

- アプリは現在サーバーを持たない。通信は気象庁と JTWC への読み取りのみで、認証機構もない。
- 永続化は UserDefaults のみ（`LocalLocationStore` が Codable ベースで JSON 保存）。
- エリア区分はコード上に存在しない。`OkinawaMunicipalityCatalog` に41自治体（沖縄県の全市町村）が座標付きで揃っている。
- タブは3つ（地図 / 場所 / 設定）。`MainTabView` が `@AppStorage("selectedTab")` で管理。
- entitlements ファイルは存在しない。Privacy Manifest は `Resources/PrivacyInfo.xcprivacy` にあり、収集データは Location のみ。
- 最低対応 iOS 17.0、外部 SPM 依存なし。

## 3. 決定事項と却下案

### バックエンドは CloudKit Public Database

- 採用理由: サーバー運用・費用がゼロで、外部 SDK を増やさず現在の「クライアント完結」方針を保てる。
- 制約として受け入れる点: 投稿には iCloud サインインが必要（閲覧は不要）。サーバー側での集約や細かいレート制限ができないため、集約はクライアントで行い、連投制限は端末ローカルで持つ。
- 却下案: Supabase（無料枠がアクセス途絶で休止する。台風アプリは平常時ほぼ無通信のため相性が悪い）、リポジトリ内の Bun+Hono レガシーバックエンド復活（ホスティング費用と運用負荷が最大で、v1 をサーバーレス構成にした方針と逆行する）。

### 投稿は選択式のみ（自由テキストなし）

- 採用理由: App Store ガイドライン 1.2 の UGC 要件（通報・ブロック・モデレーション体制）を実質的に回避でき、誹謗中傷や誤情報の混入も原理的に起きない。「わかりやすい言葉」という要件とも合致する。
- 却下案: 自由テキスト併用。臨場感は上がるが、通報導線・ユーザーブロック・NG ワードフィルタ・運用体制が審査上ほぼ必須になり、実装量と審査リスクが大きく増える。

### 4つ目のタブ「みんな」を新設

- 採用理由: 既存3タブはいずれも役割が明確で割り込みにくい。
- 却下案: 地図タブへの統合。画面数は増えないが、既に最大ファイルである `TyphoonMapView`（776行）がさらに肥大化し、地図の情報密度も上がる。

### エリア区分は気象庁の細分区域（class15）に従う

- 採用理由: 割当が主観にならず、根拠を示せる。気象庁自身が「体感が異なる」前提で分けている区域と一致する。
- 当初案からの修正: 慶良間・粟国諸島（渡嘉敷・座間味・粟国・渡名喜の4村）が当初の9エリアから漏れていた。気象庁は本島中南部を「南部 / 中部 / 慶良間・粟国諸島」に分けており、この4村は独立区域である。那覇や南部に混ぜると離島の体感が本島市街の色に埋もれるため、10エリア目として独立させる。
- 検証方法: `https://www.jma.go.jp/bosai/common/const/area.json` の class15 と、offices 471000〜474000 の階層を突き合わせて確認した。

## 4. エリア定義

`OkinawaArea` enum を新設し、`OkinawaMunicipality` に `area` を割り当てる。41自治体がちょうど1エリアに属する。

| エリア | ケース名 | 自治体（計41） |
|---|---|---|
| 那覇 | `naha` | 那覇市 |
| 南部 | `south` | 浦添市, 糸満市, 豊見城市, 南城市, 西原町, 与那原町, 南風原町, 八重瀬町 |
| 中部 | `central` | 宜野湾市, 沖縄市, うるま市, 読谷村, 嘉手納町, 北谷町, 北中城村, 中城村 |
| 北部 | `north` | 名護市, 国頭村, 大宜味村, 東村, 今帰仁村, 本部町, 伊江村, 恩納村, 宜野座村, 金武町, 伊平屋村, 伊是名村 |
| 慶良間・粟国 | `keramaAguni` | 渡嘉敷村, 座間味村, 粟国村, 渡名喜村 |
| 久米島 | `kumejima` | 久米島町 |
| 宮古 | `miyako` | 宮古島市, 多良間村 |
| 石垣 | `ishigaki` | 石垣市, 竹富町 |
| 与那国 | `yonaguni` | 与那国町 |
| 大東 | `daito` | 南大東村, 北大東村 |

割当の注意点:

- 浦添市は地理的には中部寄りだが、気象庁の区分では南部である。区分に従う。
- 伊平屋村・伊是名村・伊江村は離島だが、気象庁も本島北部に含めるため北部にまとめる。
- 竹富町は西表・波照間など広域だが、気象庁が石垣島地方として同じ上位区分に置くため石垣にまとめる。

現在地からのエリア判定は、既存の `OkinawaMunicipalityCatalog.nearest(to:)` で最寄り自治体を求め、その `area` を使う。

## 5. 体感レベルと定型フレーズ

体感は5段階。色・表情・ラベルがレベルと1対1に対応する。色覚多様性に配慮し、色だけに頼らず表情と文字を常に併記する。

| レベル | 色 | 表情 | ラベル |
|---|---|---|---|
| 1 | 青 | 😌 | おだやか |
| 2 | 緑 | 🙂 | 風が出てきた |
| 3 | 黄 | 😟 | 雨風が強い |
| 4 | 橙 | 😨 | 外は危険 |
| 5 | 赤 | 😱 | 暴風 |

定型フレーズは `MoodPhraseCatalog` が持つ静的カタログで、レベルごとに4件。CloudKit には `phraseID` のみ保存し、文言はアプリ内で解決する。これにより後から文言を修正でき、投稿内容が選択式に限定されることも保証される。

フレーズの初期案:

- レベル1: 「まだ静か」「風は穏やか」「雨は降っていない」「普段どおり」
- レベル2: 「木が揺れている」「雨が降り始めた」「買い出しに行った」「まだ出歩ける」
- レベル3: 「窓が音を立てている」「外出はやめた」「交通が乱れている」「傘がさせない」
- レベル4: 「外に出られない」「物が飛んでいる」「停電しています」「断水しています」
- レベル5: 「風の音がすごい」「窓から離れている」「峠はまだ先」「峠を越えたかも」

フレーズはレベルのラベルと重複させない。ラベルとフレーズは画面に並べて表示するため、同じ文言だと情報量がゼロになる。

ID は文言と独立させ、文言を変えても過去投稿の意味が壊れないようにする。

## 6. アーキテクチャ

```
AreaMoodView（新タブ「みんな」）
   └─ AreaMoodViewModel
        ├─ MoodPostStore（protocol）
        │    ├─ CloudKitMoodPostStore（本番: Public Database）
        │    └─ InMemoryMoodPostStore（テスト・スクリーンショットモード用）
        ├─ MoodAggregator（純関数: 投稿列 → エリア別の代表体感）
        ├─ MoodPhraseCatalog（定型フレーズの静的カタログ）
        └─ MoodPostRateLimiter（連投制限。UserDefaults）
```

既存コードへの変更は次の2点に限る。

- `MainTabView` にタブを1つ追加する。
- `OkinawaMunicipality` に `area` プロパティを追加し、41件に値を与える。

`MoodPostStore` を protocol にすることで、CloudKit に触らずに ViewModel と集約ロジックをテストできる。

## 7. データモデル

CloudKit レコードタイプ `AreaMoodPost`:

| フィールド | 型 | 合成例 |
|---|---|---|
| `area` | String | `"keramaAguni"` |
| `level` | Int64 | `4` |
| `phraseID` | String | `"L4_power_outage"` |
| `creationDate` | Date（CloudKit システム項目） | `2026-08-15T14:32:07Z`（ISO 8601 / UTC） |

投稿時刻はシステムの `creationDate` を使い、アプリ側では書式化して保存しない。表示時のみ相対時刻（「12分前」）に変換する。

精密な位置情報は送信しない（エリアIDのみ）。ユーザーを識別する値も持たせない。

## 8. データフロー

- 取得タイミング: タブ表示時、プルリフレッシュ時、表示中は5分間隔。
- クエリ: 直近3時間の投稿を `creationDate` 降順で1回取得する。取得上限は200件とする（10エリア×直近20件相当で、集約の代表値を決めるには十分な量）。
- 集約: `MoodAggregator` がエリアごとに最頻レベルを代表値とする。同数の場合は高いレベル側に倒す（防災文脈では見逃しより過剰の方が安全）。投稿が0件のエリアはグレーの「投稿なし」。
- 失効: 3時間より古い投稿はクエリで除外されるだけ。v1 ではサーバー側の削除処理を持たない（レコードが小さく件数も限られるため）。
- 投稿後は取得を待たず、自分の投稿を楽観的に反映する。

## 9. UI

### みんなタブ

- 10エリアを沖縄の地理関係に沿って配置したグリッド（与那国が西端、大東が東端）。各セルにエリア名・代表表情・集約色・投稿数を表示。
- 画面上部に「みんなの体感（公式情報ではありません）」を常時表示。
- 下部に投稿ボタン。

### エリア詳細シート（セルをタップ）

- レベル分布のバー、直近投稿のリスト（相対時刻・表情・フレーズ）。

### 投稿フロー（3タップ）

1. エリア選択（現在地から自動判定して初期選択、変更可）
2. レベル選択（色＋表情＋ラベル）
3. フレーズ選択 → 送信

匿名・アカウント登録なし。連投制限は同一端末10分に1回とし、制限中は残り時間を表示する。iCloud 未サインイン端末では閲覧は可能で、投稿時のみ「投稿には iCloud サインインが必要です」と案内する。

## 10. エラー処理

- 取得失敗時は最後に取得できた結果を表示したまま、既存の `DataSourceStatusBanner` と同じ流儀で「更新できませんでした」を示す。無言で失敗させない。
- CloudKit のレート制限エラーは `retryAfter` を尊重して再試行する。
- 投稿失敗はその場で通知し、選択内容を保持して再送できるようにする。
- 位置情報が取得できない・許可がない場合はエリアを自動選択せず、ユーザーに選ばせる。位置情報の許可要求はユーザー操作時のみ行う（既存方針の踏襲）。

## 11. プライバシー・審査対応

- `PrivacyInfo.xcprivacy` の `NSPrivacyCollectedDataTypes` に、エリア（粗い位置に相当）を非リンク・非トラッキングで追加する。App Store Connect の App Privacy 回答も更新する。
- entitlements ファイルを新規作成し、CloudKit コンテナを追加する。xcodegen 運用のため `ios/project.yml` に定義を書く。
- 選択式のみのため UGC のモデレーション導線（通報・ブロック）は v1 では持たない。
- リリース手順に CloudKit スキーマの本番環境デプロイを組み込む。開発環境で作成したレコードタイプは、本番ビルドから参照する前に Production へデプロイする必要がある。これを忘れると審査時に機能が動かない。

## 12. テスト方針

純関数を厚くテストする。

- `MoodAggregator`: 最頻値、同率時のタイブレーク（高レベル優先）、3時間の時間窓の境界、0件エリアの扱い。
- エリア割当: 41自治体すべてがちょうど1エリアに属することの全数検査。各エリアが1件以上持つこと。
- `MoodPhraseCatalog`: ID の重複がないこと、全レベルにフレーズが存在すること。
- `MoodPostRateLimiter`: 10分境界の前後。
- `AreaMoodViewModel`: `InMemoryMoodPostStore` を使い、取得→集約→表示、投稿→楽観的反映、取得失敗時に前回結果を保持することを検証する。

スクリーンショットモード（`-screenshotMode YES`）ではサンプル投稿を表示し、CloudKit には書き込まない（既存方針の踏襲）。

シミュレータ検証は「既存データあり・再起動後」を標準条件とする（過去に揮発バグを見逃した教訓による）。

## 13. v1 でやらないこと

自由テキスト投稿、通報・ブロック、リアクション（いいね等）、投稿の削除UI（数時間で自然に失効するため）、時系列チャート、プッシュ通知連動、古いレコードの掃除バッチ、英語ローカライズ（既存機能に合わせ日本語のみ）。
